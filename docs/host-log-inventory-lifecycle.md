# 主机日志源清单生命周期

日志目录和项目归属是两个独立维度。每个 `files[]` 条目代表一个可审计的日志源，必须包含稳定的 `id`、环境、项目、服务、格式、明确的 `include` 和只读 `mounts`。目录可以轮转或迁移，`id` 不得因路径变化而复用；路径变化应在同一条目中记录变更并保留 checkpoint，只有日志语义变化才新建条目。

## 增加服务

1. 先确认日志根目录、文件后缀、所有者和是否与其他主机/NFS 共享。
2. 在对应环境的 inventory 增加条目，使用新的稳定 `id` 和服务名；PHP 服务名必须以 `php_` 开头。
3. 运行渲染器、静态校验和 Vector 配置验证，检查目录没有覆盖 cache、session、upload 或 Nginx 日志。
4. 先以候选配置观察文件发现、正文 `message`、多行边界和后端字段，再纳入长期配置。

## 下线服务

将条目标记为 `status: draining`，停止新增采集并观察 checkpoint 和 buffer 排空；保存最后一次清单、配置和 source 状态后再移除 Compose 挂载。至少保留一个完整保留周期的旧 Topic/日志查询能力，之后才删除条目。`id` 永不重新分配给新服务。

## 项目归属变化

项目变更会影响 Topic、ACL、消费者组和 Dashboard 检索。不得直接修改已入库日志的历史标签。为新项目生成新路由和身份，在切换窗口停止旧路由、启动新路由，并用 source offset、时间窗口和样本正文对账。若只是显示名变化，只改项目登记表，不改 project ID、Topic 或 source ID。

## 环境边界

阿里云测试清单只能指向测试 VictoriaLogs，禁止出现生产 AutoMQ 凭据；华为云生产清单才允许使用生产 AutoMQ 路由。广西政务云生产目录不登记，广西测试目录单独登记在阿里云测试主机。每次变更都要在清单中写明环境，避免复制配置时串环境。

## 目录布局

每台主机的持久化目录固定为 `/data/vector/<environment>/`，包含 `inventory.yaml`、生成的 `config/`、独立 `state/`、`backups/` 和权限为 `0600` 的 secrets。清单是唯一事实来源，Compose 和 Vector 配置均由它生成；禁止现场手改生成文件。
